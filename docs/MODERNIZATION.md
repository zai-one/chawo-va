# План модернизации Chawo VA (октябрь 2026)

Цель — привести приложение к современному стеку, близкому к ZAI, не потеряв ни одной функции 2.0
и ни одного теста. Веб-кабинет в этот план не входит: он появится позже вместе с доработками сервиса.

Правила продукта остаются прежними: только тёмная тема, без телеметрии, ключи не хранятся в
репозитории, всё локально по умолчанию, короткие меню.

## Целевой стек

| Часть | Было (2.0) | Станет |
|---|---|---|
| Окно приложения | Electron 38 (поддержка закончилась) | **Electron 44** (Node 24 внутри) |
| Локальная логика и CLI | Node ≥ 20, CommonJS | **Node 24+**, TypeScript |
| TypeScript | 5.9 | **6.0** (TS 7 пока не поддерживается typescript-eslint; переход — когда появится поддержка) |
| Интерфейс | Один файл `renderer.ts` (2860 строк), голый DOM | **React 19** + пакет `@chawo/ui` (CSS-токены и свои компоненты) |
| Сборка | `tsc` + скрипт копирования | **Vite 8 + electron-vite 6**: main, preload, интерфейс и CLI одним конфигом, HMR в разработке |
| Связь интерфейса с системой | preload отдаёт `unknown`, каналы строками в трёх местах | **Типизированный IPC**: один контракт в `@chawo/ipc`, проверка аргументов, проверка отправителя |
| Локальные данные | JSON и JSONL | **SQLite** (встроенный `node:sqlite`, без нативной пересборки) для истории, журнала CRM и вопросов; настройки — JSON с атомарной записью |
| Секреты | `safeStorage`, а токены CRM — открытым текстом | **Системное хранилище ключей** (Windows Credential Manager, macOS Keychain, Secret Service) через `@napi-rs/keyring`, общее для приложения и CLI |
| Проверки | Vitest 3, TypeScript | **Vitest 5, Playwright, ESLint 10, TypeScript, Knip** |
| Структура | папка `ts/` на npm + старый WPF рядом | **pnpm workspaces**; WPF — в `legacy/` |
| Установщик Windows | electron-builder, NSIS + ZIP, без подписи | то же + **Electron fuses**, проверка целостности ASAR, подпись при наличии сертификата |

## Структура монорепозитория

```
package.json, pnpm-workspace.yaml   общие скрипты: lint, typecheck, test, knip
apps/
  desktop/        Electron: main, preload, renderer (React), окна, IPC, упаковка, ChawoNative, e2e
  cli/            chawo-va: команды CLI (собирается в пакет приложения как dist/cli.js)
packages/
  core/           @chawo/core — логика без Electron и без файловой системы (бывший ts/src/core)
  engine/         @chawo/engine — сервисы на Node без Electron: настройки, хранилище, секреты,
                  очередь файлов, модели, Мозг, сеть, CRM, история, MCP, встречи
  ipc/            @chawo/ipc — контракт IPC: каналы, типы состояний страниц, схемы аргументов
  ui/             @chawo/ui — токены, базовые компоненты React
legacy/wpf/       старое приложение WPF (только для справки, сборка вручную)
docs/             документация, этот план
```

CLI запускается тем же `ChawoVoiceAssistant.exe` в режиме Node (`ELECTRON_RUN_AS_NODE`), поэтому
fuse `RunAsNode` остаётся включённым — иначе перестанет работать `chawo-va.cmd`.

## Этапы

Каждый этап — отдельные коммиты. Перед каждым пушем: проверка типов, линтер, все unit-тесты,
сборка и e2e-смоук под xvfb. Ни один тест не отключается и не удаляется.

1. **Рантайм и инструменты.** Electron 44, Node 24, TypeScript 6.0, Vitest 5, `@types/node` 24.
   CI на Node 24. Починить всё, что сломается при обновлении.
2. **Линтеры.** ESLint 10 (flat config, typescript-eslint, правила для React hooks), Knip
   (неиспользуемые файлы, экспорты, зависимости). Найденное исправить, а не отключить.
3. **Настройки без Electron.** Вынести защиту секретов из `settings.ts` в подключаемое хранилище:
   тогда почти весь main работает без Electron, и его можно отдать в `@chawo/engine`.
4. **pnpm-монорепозиторий.** Перенос в `apps/*` и `packages/*`, тесты рядом с пакетами,
   один `vitest` с проектами. WPF — в `legacy/wpf`, его сборка по тегу отключается
   (сейчас по тегу `v*` собираются обе версии).
5. **electron-vite.** Сборка main, трёх preload, трёх окон интерфейса и CLI. `copy-static.mjs`
   больше не нужен. Режим разработки с горячей перезагрузкой интерфейса.
6. **Типизированный IPC.** Контракт в `@chawo/ipc`: каждое `invoke`/`send`/событие описано один раз.
   preload строится по контракту, обработчики в main получают проверенные аргументы, запросы не
   из окон приложения отклоняются. Типы состояний страниц больше не дублируются в интерфейсе.
7. **React 19 и `@chawo/ui`.** Токены (цвета, отступы, радиусы, шрифты) и компоненты (кнопка,
   поле, переключатель, список, карточка модели, прогресс, уведомление). Страницы переносятся по
   одной: Сеть → Словарь → Продажи → История → Распознавание → Мозг → Диктовка → Расшифровка файла
   → Запись встречи; затем плашка и карточка продаж. Поведение и тексты не меняются.
8. **Данные и секреты.** SQLite для истории, журнала CRM и истории вопросов, с миграцией из
   JSON/JSONL при первом запуске (старые файлы сохраняются как `.bak`). Атомарная запись
   `settings.json`. Токены CRM, ключи облачных провайдеров и прочие секреты — в системное
   хранилище ключей с переносом из файлов. Если хранилище недоступно (Linux без Secret Service),
   приложение говорит об этом явно, а не теряет ключ молча.
9. **Playwright.** e2e через `_electron`: запуск, навигация по страницам, ключевые сценарии;
   существующие смоук-скрипты конвейеров остаются.
10. **Безопасность и релиз.** Electron fuses (кроме `RunAsNode`), проверка целостности ASAR,
    подпись Windows-сборки через секреты CI (включается, когда появится сертификат),
    Dependabot для npm и GitHub Actions, актуальные версии actions.

## Решения по умолчанию (можно поменять)

- **Обновления** остаются ручными: приложение только проверяет новую версию и открывает страницу
  релиза. Автообновление (`electron-updater`) имеет смысл включать только вместе с подписью кода.
- **Подпись кода.** Сертификата в репозитории нет; конфигурация будет готова принять его через
  секреты `CSC_LINK`/`CSC_KEY_PASSWORD` (или Azure Trusted Signing).
- **WPF** не удаляется, а переносится в `legacy/wpf` и собирается только вручную.
- **TypeScript 7** — следующий шаг, как только typescript-eslint объявит поддержку.

## Риски

- Перенос файлов в монорепозиторий конфликтует с параллельными ветками. На момент начала открытых
  PR нет; новые ветки лучше начинать уже от модернизированной структуры.
- Сборку Windows (NSIS, ChawoNative) нельзя проверить на Linux; для неё запускается workflow
  «TS Windows» на ветке модернизации.
